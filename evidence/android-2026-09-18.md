## Fixes (step 2b) — `hem-96-fixes` @ `c340770`

One commit on `hotmic-core-android-source`, public API unchanged (`core/api/core.api` byte-identical; `apiCheck`
clean, no `apiDump`), 80 unit tests (63 + 17 new in `SessionResilienceTest` and `PollCursorCatchUpTest`). What
changed and why is tabulated in `evidence/android-notes.md`; in short: row-tolerant `poll-data` decoding with

follows `delta.window.to` with immediate catch-up polls (F15), `HotMicLogger` under tag `HotMicCore` (F16),
`stream_poll_timeout` applied (F17). F18 not changed (needs a public `close()`; opinion in the notes).

## Load (§2) — 25 and 250 real SDK sessions from one JVM, stream `71e76bb9` (LIVE before every tier)

Harness: `LiveLoadTest.kt` (`hem-96-core-load` @ `b36a88b`; see `LoadTest/README.md`), driven by
`LoadTest/run-tier.sh` (confirms `LIVE`, `load/preflight.log`). N real `HotMicClient` + `HotMicStreamSession` pairs
in one JVM (JDK 17.0.20, this Mac, `host=Chriss-MacBook-Pro-3.local` in every `<tag>-events.log`); the only
injected piece is the SDK's internal `httpClient` seam — one `OkHttpClient` (no cache, like the public default)
and one `hm-device-id` per session, one logging interceptor. Ramp 5/s · hold 300 s · drain 10/s · idle 120 s;
chat 1 msg/30 s per chatting session (100 % at 25, 20 % = 50 sessions at 250); presence checks at ramp end /
hold midpoint / hold end / idle end. Stop rules (every 5 s): any 429 · ≥ 2 % non-2xx over 60 s · poll-data p95
> 2 s over 60 s · > 5 % sessions reconnecting/failed · rate > 1.5× budget · STOP file. Budget per session
0.358 rps (poll 3 s + presence 60 s + viewers 120 s, verified from the request log) + chat share. `baseUrl`
stayed the SDK default (prod). The 5,000 tier was **not** run (per the addendum).

Every number below is recomputed from the raw files by `summarize-tier.py` (the tier rows are its `--md`
output verbatim). SDK on `main` @ `51de67e` for the first three tiers, `hem-96-fixes` @ `c340770` for the last
two. The 30-minute emulator soak (N20) overlapped the three `main` tiers on the same stream. Transport errors
are all `IOException Canceled` / `StreamResetException` on `poll-data` at drain time (the SDK's own
`stopPolling()` cancelling an in-flight poll), never during hold. No stop rule tripped in any tier; every

Notes on the tables:
- **Edge vs origin** is the same picture as iOS-B: the SDK floors `from`/`to` to the second, so sessions that
  start in the same wall-clock second request identical `poll-data` URLs for life and CloudFront (`cache-control:
  public, max-age=3`, key ignores `Authorization`/`hm-device-id`) answers all but one per 3 s window — the API
  origin saw **0.33 poll-data/s at 250 sessions** (100 misses in 300 s) plus the non-cacheable presence
  (4.2/s), chat and join traffic. Hit p95 ≈ 210–260 ms is the same unexplained fat tail iOS saw.
- **Presence** is per user: 25 sessions on one JWT count as 1 viewer (the "1" in the shared rows is the emulator
  soak's session on the same user); 25 minted users count as 25 (+1 soak) and drop to 0 within 2 min of
  `end_session` once the soak had ended (`tier25-fixes-users` idle end = 0).
- **Chat delivery on Android with a shared JWT is observable** (unlike iOS): the harness gives every session its
  own `hm-device-id`, and the SDK's own-message filter is user *and* device, so 25 sessions on one user still
  see each other's messages. Duplicate deliveries on `main` are 9.7–10.5 % of deliveries in every tier, always
  exactly one poll (3 s) after the first copy (F2); **0 on `hem-96-fixes`** at both 250 and 25-users with the
  same latency and completeness (unique deliveries 20 506 vs 20 671 at 250 with 541 vs 537 sends).
- Latency rows "excluded": the first harness revision parsed `created_at` with a shared `SimpleDateFormat` (not
  thread-safe); the summarizer keeps only rows whose `created_ts` equals the majority value for that message id
  (see `android-notes.md`, "Corrections"). p50/p95 are stable across the filtered sets (3.2–3.5 s / 5.2–5.8 s);
  max ≈ 7 s = server window lag + 3 s poll + 1 s chat batch.
- Peak MB is the whole test JVM's RSS (`ps`), 250 sessions ≈ 500–570 MB; not comparable to a device.
